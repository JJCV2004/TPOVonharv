Comparativa de Código & Justificación de Ingeniería

Análisis detallado de la vulnerabilidad en Python/SQLite y su remediación mediante buenas prácticas.

MALA PRÁCTICA formulario_vulnerable.py
Vulnerable a SQLi & XSS 
# [FALLA 1]: Conexión sin manejo seguro ni validación
import sqlite3

def guardar_presupuesto_vulnerable(tipo, fecha, nombre, comentarios):
    conn = sqlite3.connect("vonharv.db")
    cursor = conn.cursor()

    # [FALLA 2]: Concatenación directa de strings (f-string)
    # Los datos del cliente se mezclan con el comando SQL del servidor.
    sql = f"""
        INSERT INTO solicitudes (tipo, fecha, nombre, notas)
        VALUES ('{tipo}', '{fecha}', '{nombre}', '{comentarios}');
    """

    # [FALLA 3]: executescript permite múltiples sentencias (DROP, DELETE)
    cursor.executescript(sql)
    conn.commit()
    conn.close()

# Si el atacante envía:
# nombre = "Juan', ''); DROP TABLE solicitudes; --"
# El comando 'DROP TABLE' es ejecutado por el motor SQL sin filtro alguno.
¿Por qué falla según la teoría de cátedra?

No existe frontera lógica entre las instrucciones del desarrollador y la entrada del usuario. El parser de la base de datos compila e interpreta el texto inyectado como comandos con permisos del usuario de base de datos.

BUENA PRÁCTICA formulario_seguro.py
Remediado con Estándares OWASP 
# [CONTROL 1]: Sanitización HTML y Expresiones Regulares
import sqlite3, html, re

REGEX_NOMBRE = re.compile(r"^[a-zA-ZáéíóúÁÉÍÓÚñÑ\s'.-]{2,80}$")

def guardar_presupuesto_seguro(tipo, fecha, nombre, comentarios):
    # Defensa por lista blanca y regex
    if not REGEX_NOMBRE.match(nombre):
        raise ValueError("Nombre con formato inválido")

    # Sanitización contra XSS (convierte <, >, & en entidades inofensivas)
    comentarios_limpios = html.escape(comentarios.strip())

    with sqlite3.connect("vonharv.db") as conn:
        cursor = conn.cursor()

        # [CONTROL 2]: Consulta Parametrizada (Prepared Statement)
        # Los marcadores '?' separan el comando de los datos.
        sql = """
            INSERT INTO solicitudes (tipo, fecha, nombre, notas)
            VALUES (?, ?, ?, ?);
        """
        
        # [CONTROL 3]: El driver envía los parámetros por canal aislado
        cursor.execute(sql, (tipo, fecha, nombre, comentarios_limpios))
        conn.commit()
¿Por qué es invulnerable?

La consulta SQL se precompila en el motor de base de datos antes de recibir los valores. Incluso si el atacante envía un comando DROP TABLE, el motor lo procesa estrictamente como una cadena literal de texto.

Argumentos Clave para la Defensa Oral frente a la Profesora

1. ¿Por qué validar en el Frontend no es suficiente?

Cualquier validación en JavaScript del navegador puede ser evadida deshabilitando scripts, usando herramientas como Burp Suite, Postman o enviando peticiones directas vía curl. La seguridad obligatoria debe residir en el backend.

2. ¿Qué normativa legal y estándar internacional aplica?

Aplica la Ley 25.326 de Protección de Datos Personales (responsabilidad legal de Vonharv) y el estándar internacional OWASP Top 10 (A03: Injection y A07: XSS) e ISO/IEC 27034 (seguridad en el ciclo de vida del software).

3. Rol del Grupo 01 como Consultor de IT

Como consultores externos, el Grupo 01 no programa los sitios web de Vonharv, sino que genera las especificaciones técnicas obligatorias y las cláusulas de SLA para auditar a la agencia web tercerizada mediante auditorías SAST y DAST.
